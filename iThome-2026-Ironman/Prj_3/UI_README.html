MiBand6BleExplorer

小米手環 6 的 BLE 唯讀探索工具 — 程式流程與架構設計
唯讀：不寫入、不認證 Python 3.13 bleak 2.0.0 ttkbootstrap 1.19.0 MVP ＋ 背景 asyncio 迴圈

這份文件講的是模組怎麼分、誰呼叫誰、狀態放在哪裡。程式碼一律以符號名稱指涉，不貼函式內容。 章節標題可以點開收合。

1. 這支工具是什麼

對小米手環 6 的 BLE 探索工具：掃描週遭裝置、連線、列舉完整 GATT 結構、讀取所有可讀的 characteristic、訂閱所有可訂閱的 characteristic，並把已知欄位解碼成看得懂的字。 命令列版與圖形介面版各一支。

唯讀是硬性規定。不寫入任何 characteristic、不嘗試華米（Huami／Zepp）認證、不修改手環上的任何設定。 理由：華米私有服務底下有韌體上傳用的 characteristic，一支不會寫入的程式出包上限低很多。 驗收方式是全專案 grep 不到 write_gatt_char。

兩支主程式，各自完全自包含

檔案形態用途
mi_band_explorer.py 命令列，互動選單 探索階段用這支。例外直接印在主控台，不會被 GUI 吃掉
mi_band_explorer_gui.py ttkbootstrap 圖形介面，MVP PyInstaller 打包的進入點，交付用

GUI 版不 import CLI 版，UUID 對照表（KNOWN_UUIDS / KNOWN_SERVICES） 與解碼器（decode_value / decode_huami_time / hexdump）各帶一份。 這是刻意的：GUI 版要能單獨搬走或打包，不用管相對路徑。代價是兩份要手動同步， 而且目前沒有任何機制會發現它們不同步了。

2. 模組設計與職責

圖形介面版（MVP）

層類別職責界線
ModelBandModel 所有 BLE 行為：scan / connect / disconnect / dump_gatt / read_all / read_one / summary / start_notify / stop_notify，全部是 coroutine 完全不 import tkinter，不持有任何 widget；對外只透過建構時注入的 emit callback 回報
ModelLogRecorder 純檔案 I/O：save_snapshot（一次性快照）、start / write / finish（即時逐行）、close_abruptly（關窗收尾） 不碰 Tk，也不認識 BLE
ViewExplorerView 建立與排版所有 widget；對外提供 set_devices / set_gatt / set_status / log_to_window / set_ui_connection_state / set_busy 等純呈現方法 完全不懂 BLE，也不持有 Presenter 的參考
PresenterExplorerPresenter 把 View 的 on_* 指向自己的處理器、送 coroutine 到背景迴圈、 輪詢佇列、集中所有日誌出口（_log）、負責關閉流程（close） 唯一同時認識 Model 與 View 的地方
—AsyncRunner 在背景 daemon 執行緒上跑一個 asyncio 事件迴圈；submit 丟工作、 shutdown 收尾 不認識 Model 也不認識 View，只認識 coroutine
View 不反向依賴 Presenter。使用者操作一律經由 View 身上的 on_scan / on_connect / on_read_one … 等屬性外露，預設值是空函式， 由 ExplorerPresenter.__init__ 逐一指派。因此 ExplorerView 可以單獨建起來跑， 什麼都不會壞，只是按了沒反應。這是與一般 MVC 寫法的主要差異。

純函式層（不屬於任何一層，兩支主程式各一份）

符號做的事

命令列版

沒有分層，是一個 Explorer 類別（持有 found / target / client）加上 main() 裡的選單迴圈，選項編號對到 actions 字典。 唯一需要留意的是 ainput()：input() 包進 asyncio.to_thread， 否則它會擋住事件迴圈，斷線 callback 永遠不會被呼叫——手環走遠了畫面上也不會有任何反應。

5. 互動流程

所有 BLE 操作走同一條骨架，差別只在最後丟出去的 coroutine：

使用者按鈕 → View.on_XXX → Presenter._xxx → Presenter._run(model.xxx())
    ├─ 若 _busy：coro.close() 後拒絕（否則留下 coroutine was never awaited 警告）
    ├─ _busy = True；view.set_busy(True) → 按鈕全禁用、游標變 watch
    ├─ AsyncRunner.submit(wrapper)   ← 這一步之後就在背景執行緒了
    │     wrapper 內：await coro，例外收成一則 log 訊息，finally 一定 emit("done")
    └─ 背景 emit(...) → queue → 主執行緒 _drain_queue() → _handle() → 更新 widget

掃描

  1. on_scan → _scan()：讀 timeout_var（解析失敗退回 8.0），先 view.set_devices([]) 清空舊清單。
  2. BandModel.scan()：BleakScanner.discover(return_adv=True)，結果按 RSSI 由強到弱排序存進 self.found。
  3. 逐筆轉成 ScanRow；勾了 Named devices only 就跳過無名稱的並計數。名稱命中 MI_BAND_HINTS 的把 is_band 設為真。
  4. emit("devices", rows) → view.set_devices()：重建 Treeview，is_band 的列套 band tag 加粗。清單為空時順手把 Connect 禁用。
  5. 另外 emit 兩三則 log 說明找到幾個、隱藏幾個、其中幾個疑似小米／華米裝置。

選裝置與連線

  1. 點選清單 → _on_device_selected：把 Treeview 的列序轉回 self._device_indices 裡的原始索引，再呼叫 on_select_device(index)。同一個函式順手把 Connect 啟用（未連線且不忙碌時）。
  2. _select_device() → BandModel.select_target() 只設 self.target，不碰 BLE；Presenter 接著更新 view.set_target()。
  3. 按 Connect → BandModel.connect()：建 BleakClient 時就把 _on_disconnect 掛成 disconnected_callback。
  4. 成功：emit("connected") → set_ui_connection_state(True)，五顆指令按鈕解禁、Scan 禁用、狀態轉綠。
  5. 失敗：印出 BleakError 原文，並補一行提示「手環同時只能被一個中央裝置連線，請先在手機關閉 Zepp Life」——這是實務上最常見的原因。

列舉 GATT

  1. BandModel.dump_gatt() 走訪 client.services，每個服務建一個 GattNode，特徵掛成子節點（標籤含 16-bit 短碼、人話說明、properties 與 handle），描述元再掛一層。
  2. emit("gatt", tree) → view.set_gatt() → _insert_gatt_node() 遞迴填入，只有第一層預設展開。
  3. 紀錄區只留服務／特徵計數，加一行「完整結構請看上方分頁」。

讀取

  1. Read All：走訪所有帶 read 屬性的特徵逐一 read_gatt_char。例外捕捉的是 Exception 而不是 BleakError——WinRT 後端會拋出不屬於 bleak 例外階層的東西。被拒的收進 denied，最後整批列出。
  2. Read（單一）：先 normalize_uuid_str，所以可以只打 16-bit 短碼（如 2a28）。無效格式直接回報，不送出請求。
  3. 兩條都走 _log_value()：先印 hexdump，再試 decode_value()；解得出來多印一行 => 開頭的人話，解不出來就只留 hex。
  4. Summary 讀的是一份寫死的七欄清單，那份清單是實機跑過一輪、確認免認證真的拿得到才寫進去的，不是照規範抄的。最後補一行提醒即時步數禁止直接讀取，要用 Start Notify。

Notify 監看

  1. on_toggle_notify → _toggle_notify() 依 self._notifying 決定送 start_notify 還是 stop_notify。
  2. BandModel.start_notify() 收集所有帶 notify 或 indicate 的特徵，逐一訂閱，失敗的只記一行不中斷；成功清單存進 self._subscribed。
  3. 封包進來時 callback 在 bleak 的執行緒上跑，它只做一件事：加上毫秒時間戳後 emit("log", …)。
  4. emit("notifying", True) → 按鈕文字改成 Stop Notify。
  5. disconnect() 一定先 await stop_notify()，避免留下沒收掉的訂閱。

存檔

  1. Save Printed Log：把視窗現有內容一次寫成 MiBand6_Log-Printed_*.txt。
  2. Start to Save Log：開一個 MiBand6_Log-Interval_*.txt 的檔案 handle，之後每一則訊息都由 Presenter._log() 順手寫進去（每行帶毫秒時間戳，寫完立刻 flush）。set_log_saving_state(True) 把 Start 禁用、Finish 解禁。
  3. Path to Save：filedialog.askdirectory，只改 recorder.save_dir，不影響已經開著的 handle。
  4. 檔案落在 <資料夾>/<YYYYMMDD>/，日期子資料夾在寫入前才建立。
Presenter._log() 是視窗與檔案共用的唯一出口。因此「即時存檔」不需要在 Model 裡埋任何東西： 只要訊息走過 _log()，就同時進了視窗與檔案。寫檔失敗也只會多印一行 FATAL，不會把整個流程炸掉。

7. 執行緒與關閉流程

兩個迴圈都想當主人：tkinter 的 mainloop() 要佔住主執行緒，asyncio 的事件迴圈也要佔住一條。 而且 Tk 的規矩很硬——widget 只能從建立它的那條執行緒去碰，從別條執行緒改一個 Label 的文字， 可能沒事，可能整個程式當掉，而且不會給一個好看的錯誤。

唯一的規矩：背景執行緒絕不碰任何 widget。一律走 queue.Queue ＋ after()。 有這一條，剩下的就是機械式搬運。

關閉流程：五個步驟，順序不能換

ExplorerPresenter.close()：

  1. 取消排程中的 after callback。不取消的話，destroy() 之後那個排程還會觸發，噴 invalid command name。放在最前面是因為後面幾步都要花時間，那段時間裡輪詢還會繼續排。
  2. 關閉日誌檔案 handle（recorder.close_abruptly()，會補一行 [System] Suddenly Closed.）。
  3. 斷開 BLE，result(timeout=5.0) 給有限等待，避免關窗卡住。
  4. 收掉背景事件迴圈（AsyncRunner.shutdown()：取消所有 pending task → await gather → loop.stop → join → close）。
  5. root.destroy()。
第 4 步的 _cancel_pending() 是掃描中途關窗不炸掉的關鍵。 必須讓 bleak 的 finally 有機會停掉 WinRT 掃描器；直接關迴圈的話， 掃描器仍會投遞廣播封包到一個已經關掉的迴圈上，噴 Event loop is closed。 所以是「先取消並等它們收尾，才停迴圈」，不是反過來。

另外兩個相關的細節：main() 用 try/finally 包住 mainloop()， 主迴圈因未預期例外或主控台中斷而結束時仍會走完同一套收尾； SetCurrentProcessExplicitAppUserModelID 必須在建立 root 之前呼叫， 否則工作列顯示的是 Python 直譯器的圖示。

8. 功能與限制

做得到

  • 掃描週遭 BLE 裝置，依 RSSI 排序，可選只列有名稱的；疑似小米／華米的裝置加粗。
  • 連線、斷線，斷線由對方發起時也會即時反映到介面上。
  • 列舉完整 GATT：服務 ▸ 特徵（含 properties 與 handle）▸ 描述元，樹狀可收合。
  • 讀取所有可讀特徵，或指定單一 UUID（支援 16-bit 短碼）；被拒的連同原因一起列出。
  • 已知欄位語意解碼：裝置名稱／序號／硬體版本／韌體版本／電池電量、標準 Current Time、 標準心率量測（含 8/16-bit 旗標）、華米電池詳情與即時步數。
  • 訂閱所有可訂閱特徵，逐筆封包帶毫秒時間戳。
  • 紀錄存檔兩種：一次性快照，或從現在開始邊跑邊寫。
  • 亮色／暗色主題切換，紀錄視窗配色同步。

做不到，或刻意不做

限制說明
不寫入、不認證硬性規定。因此需要 auth key 的欄位（心率控制點、多數華米私有欄位）永遠讀不到，這不是 bug
同時只能一個中央裝置連線手機的 Zepp Life 沒關掉就連不上，這是手環的行為不是程式的
連線中途手環走遠沒有處理斷線通知路徑是通的，UI 也會打回未連線；但若斷在「讀取所有可讀特徵」跑到一半， 後面幾十個會一個一個失敗、每個印一行錯誤，畫面被洗版。合理做法是在迴圈裡檢查連線狀態、斷了整批中止——知道要做，還沒做
兩份表遲早不同步UUID 對照、解碼器、Summary 那七欄清單都各有兩份。目前一致是因為同時寫的。 要嘛抽成共用模組，要嘛加一個測試去比對——兩個都還沒做
解碼器只涵蓋看得懂的那幾個華米私有欄位還有不少沒解，即時活動封包後面幾個位元組也沒解。 這個是刻意停的：再往下就要靠猜，猜出來的東西沒辦法驗證
打包版沒有標準輸出console=False，探索階段要看主控台就直接跑 .py
只在 Windows 驗過bleak 本身跨平台，但這裡的 WinRT 相關處理、app.ico、AppUserModelID 都是 Windows 專屬
視窗最小 1100×700三段式版面在更窄的視窗會擠在一起
不是為了什麼設計的。這不是手環管理工具，也不是資料同步工具——它不會改手環上的任何東西， 也不會把活動資料抓回來。它只回答一個問題：這支裝置在未認證的情況下，願意給什麼。

9. 已經做過的決定

決定結論理由
唯讀硬性規定華米私有服務底下有韌體上傳用的 characteristic，一支不會寫入的程式出包上限低很多
兩支主程式各自自包含不共用模組GUI 版要能單獨搬走或打包；代價是兩份手動同步
先做命令列版圖形介面留到後面tkinter 的 callback 裡出事，預設只在主控台印一行然後繼續跑，視窗上什麼都不會發生
UI 設計稿選了實作代價最低的那張Main（litera 色票、三段式）另外兩張的圓角、陰影、固定側欄在 ttk 裡沒有對應物；未採用那張的深色色票整組搬進程式當暗色主題
打包方式只做 onefile實測 21.5 MB、冷啟 7.4 秒、之後約 4.5 秒，都在可接受範圍；探索階段本來就直接跑 .py
hiddenimports留空原本抄了七個 winrt.*，實測拿掉之後 exe 照樣掃得到裝置、體積也一樣——內建的 bleak hook 已經收乾淨了
圖示tools/make_icon.py 產生，六種解析度錶面＋兩道廣播弧。置中同心扇形試過，縮到 16px 跟 Wi-Fi 圖示分不出來
ttkbootstrap 主題亮 litera／暗 darkly設計稿直接取用 litera 色票，確保畫得出來的東西 ttk 真的做得到

踩過的坑（改程式前先看這幾條）

  • .spec 必須在 Analysis(...) 之前把 <sys.prefix>\Library\bin 加進 PATH。少了它建置照樣 exit 0，.exe 啟動時死在 ImportError: DLL load failed while importing _ctypes。驗收看的是建置紀錄裡 Library not found 為 0，不是 exit code。
  • 關閉流程的五個步驟不能換順序（見第 7 節）。
  • 本環境的 ttkbootstrap 只有 Panedwindow（小寫 w）。
  • SetCurrentProcessExplicitAppUserModelID 必須在建立 root 之前呼叫。
  • _run() 拒絕重複送出時要 coro.close()，否則留下 coroutine was never awaited 警告。
  • scrolledtext.ScrolledText 不隨 ttk 主題連動，切主題要自己重上色。
  • 背景執行緒不得碰任何 widget。
MiBand6BleExplorer — 架構文件。對應原始碼：mi_band_explorer.py、 mi_band_explorer_gui.py（Python 3.13 / bleak 2.0.0 / ttkbootstrap 1.19.0）。 專案摘要見 README.md；給非開發者的操作手冊是 使用者指引.html。
